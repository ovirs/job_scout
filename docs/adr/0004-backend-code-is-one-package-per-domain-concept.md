# Backend code is one package per domain concept, each owning its routes, schemas, tables and rules

The webapp backend is organised as one Python package per domain concept (`job_postings/`, `clippings/`, `evaluations/`, `triage/`, `applications/`, `notes/`, `cover_letters/`, `user_inputs/`, and later the Pipeline concepts). Each package holds the same files whatever its size: `routes.py` (a FastAPI router that parses requests, calls the package and maps its errors to HTTP, with no rules of its own), `schemas.py` (the Pydantic request and response models), `models.py` (its SQLAlchemy tables) and `domain.py` (its rules and queries). We chose this over the flat layout, with one shared `api.py` and `models.py` that every ticket edited, and over a layered layout (`routes/`, `services/`, `dao/`, `utils/`), which spreads one feature across five folders and invites pass-through modules. The aim is that a change to one concept stays inside one folder. We accept the ceremony of identical files for small concepts in exchange for a layout every package shares.

## Considered Options

- **Flat modules with a shared `api.py` and `models.py`** (what we had): simple imports and one view of every table, but the two shared files conflicted between branches, and domain rules drifted into the route handlers.
- **Layered (`routes/`, `services/`, `dao/`, `utils/`)**: familiar, but low locality. A DAO layer would be a seam with a single implementation, since tests run against real Postgres.
- **Tables kept together in one `db/` package**: easier relationships, but it breaks the rule that a package holds everything about its concept. We chose consistency.

## Consequences

- **Packages depend in one direction.** A package may import only from the packages below it. Code that coordinates several concepts lives in the highest package involved, never in `routes.py`, and never in a lower package reaching up. The order is written down alongside the code, and is checked whenever a package is added.
- **Shared code lives in a module named for a concept** (for example the posting text the LLM reads, or the LLM job run). There is no `utils/` or `common/`.
- **Foreign keys name tables by string**, so they need no imports between packages. A `relationship()` to a lower package imports the class. A `relationship()` to a higher package is the one allowed exception: the class name is quoted and imported only under `TYPE_CHECKING`, so nothing is imported upward at runtime. Each exception should be removed when its concept is next reworked.
- **`job_scout/tables.py` imports every package's `models.py`**, so SQLAlchemy can resolve quoted class names and Alembic sees every table. The API, the worker and `alembic/env.py` import it at startup, and a test checks that every package's tables are registered. A package left out of the registry is invisible to autogenerated migrations.
- **The generated frontend client is unaffected** by splitting routers, because operation ids come from the route function names.
